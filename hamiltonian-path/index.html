01 · The idea

Extend the path. Undo the last step if stuck.

A Hamiltonian path visits every vertex in a graph exactly once. There's no shortcut rule like Sudoku's row/column/box check — the only way to know a partial path is doomed is to keep extending it until it provably can't reach the remaining vertices, then backtrack.

The three moves, again

Choose an unvisited neighbor of the path's current last vertex.

Explore — recurse, assuming the path continues from there.

Un-choose — if every neighbor from here leads nowhere, remove the last vertex and let the caller try a different one.

Unlike Sudoku, there's no local constraint that instantly rules out most wrong guesses — a path can look perfectly fine for five, six, seven steps and only fail because the one remaining unvisited vertex has no edge back to where the path ended up.

Path vs. cycle

This demo looks for a Hamiltonian path (start anywhere, end anywhere, visit every vertex once) rather than a Hamiltonian cycle (which must also return to the start). The backtracking shape is identical either way.

No — determining whether a Hamiltonian path exists at all is NP-complete. Backtracking is a correct way to find one when it exists, but there's no known algorithm that's fast on every graph.
02 · Why not brute force?

The obvious approach, first

Before backtracking, it's worth seeing the approach it replaces: generate every possible ordering of the vertices, then check whether consecutive vertices in that ordering are actually connected by an edge.

Generate & test

List every permutation of the n vertices, then walk each one checking whether every consecutive pair is joined by an edge in the graph. If any pair isn't connected, discard that entire ordering and move to the next permutation.

This graph has 7 vertices, so brute force would consider up to 7! = 5,040 orderings (or 6! = 720 if the start vertex is fixed, as it is here) before checking a single edge. On a 20-vertex graph that same idea means roughly 19! ≈ 1.2 × 1017 orderings — this is where the two approaches' practical difference becomes enormous.

What backtracking changes

Instead of building a full ordering and checking it once at the end, backtracking checks for an edge the moment it tries to extend the path to a new vertex. An extension that isn't actually connected is never explored further — no time is spent completing an ordering that was already impossible after its second step.

Not really — it's the same generate-and-test idea, just interleaved with validation instead of run afterward. That's the entire trick: it turns "check every finished ordering" into "check one edge at a time and abandon impossible paths immediately."
03 · The algorithm

Twelve lines, read top to bottom

This is the exact function the live demo executes — neighbors of the current last vertex are tried in ascending order, starting the path at vertex 0.

function solve(path, depth) {
  if (path.length === n) return true; // visited all
  const last = path[path.length - 1];
  for (const next of neighbors(last)) {
    if (isValid(next, path)) {
      path.push(next);              // place
      if (solve(path, depth + 1)) return true;
      path.pop();                   // undo (backtrack)
    }
  }
  return false;  // dead end, let caller backtrack
}

Base case (line 2)

Once the path's length equals the number of vertices, every vertex has been visited exactly once — the recursion unwinds with true.

The recursive step (lines 4–9)

isValid just means "not already on the path". A valid neighbor extends the path, then solve() recurses from that new last vertex. If that returns false, line 8 removes it before the loop tries the next neighbor.

06 · Complexity & trade-offs

What backtracking actually buys you

n is the number of vertices (7 here). Both approaches share the same worst-case bound — there's no local rule here (unlike Sudoku's row/column/box check) to prune most branches early, so the gap between them is smaller than in the other two demos, but backtracking still avoids fully building orderings that fail early.

Time & space

MetricBrute forceBacktracking
Best caseΩ(n!) — still generates every orderingO(n) — a valid path found on the very first attempt at each step
Worst caseO(n!·n) — generate, then validate each orderingO(n!) — same bound, pruned as soon as an edge is missing
SpaceO(n) per candidate ordering heldO(n) recursion depth + the path/visited arrays

On this graph: brute force checks up to 6! = 720 orderings (start fixed); the live demo you ran needed 199 steps.

Advantages & disadvantages

  • Abandons an ordering the instant an edge is missing, instead of building it fully first
  • Simple and general — works on any graph, directed or undirected, without modification
  • Complete: guaranteed to find a Hamiltonian path if one exists
  • Extends naturally to Hamiltonian cycles by requiring a final edge back to the start
  • Worst-case time is factorial — the worst family of problems in this entire deck
  • No cheap local constraint (like Sudoku's row/box rule) to prune most branches early
  • Sparse, tricky graphs can force deep backtracking with little advance warning
07 · Alternative approaches

Smarter than plain backtracking

Two techniques that push past factorial-time backtracking, at the cost of memory or of a strict worst-case guarantee.

Bitmask dynamic programming

Represent "which vertices have been visited" as a bitmask, and let dp[mask][v] mean "a path visiting exactly the vertices in mask, ending at v, exists." Building this table bottom-up costs O(2n·n) time and O(2n·n) space — still exponential, but a dramatic improvement over O(n!) for moderate n (this is the same Held–Karp idea used for the Traveling Salesman Problem).

2n·n grows far slower than n! — for n = 20, n! is about 2.4 × 1018 while 2n·n is about 2 × 107. The DP table does use real memory, which is why this approach stops being practical once n gets into the high 20s or 30s.

Branch and bound

Keep backtracking's exact search structure, but add a bounding check before recursing: for instance, verify the remaining unvisited vertices are still reachable from the current position at all, or that no unvisited vertex has become totally cut off. Branches that fail the check are skipped without ever being explored — the worst-case bound is unchanged, but many real graphs see a large chunk of the search tree pruned away.

08 · Real-world applications

The same shape shows up outside graphs

"Visit everything exactly once, following only the connections that actually exist" turns out to describe quite a few practical problems.

Task sequencing

When tasks (or job-shop operations, or DNA fragments in sequencing-by- hybridization) must each be performed exactly once and only certain orderings are physically or logically valid, finding a feasible full sequence is exactly a Hamiltonian path search over a graph of "can follow" relationships.

Network traversal

Inspection routes, certain vehicle-routing variants, and network-testing procedures that need to visit every node in a network exactly once (rather than find the shortest tour, which is the related Traveling Salesman Problem) reduce directly to Hamiltonian path search over the network's connectivity graph.
